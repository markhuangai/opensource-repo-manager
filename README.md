# opensource-repo-manager

GitHub Actions maintenance that investigates selected issues, prepares audited and tested fixes, follows PR feedback, and publishes readiness for human review. Each invocation uses a temporary Linux container and exits when work completes, blocks, or must wait.

The image's default entrypoint is the bounded Actions runtime. Authenticated GitHub comments hold task authority; encrypted Actions artifacts retain recoverable sessions. Human review and merge remain required.

## Install bounded Actions maintenance

The reusable workflow runs temporary Docker containers for issue investigation, clarification, audited fixes, PR repair, and readiness monitoring. It needs no webhook server, GitHub App, external database, or state branch. Authenticated issue comments retain task authority; encrypted Actions artifacts retain recoverable native sessions for 14 days. A human still reviews and merges every PR.

1. Copy `examples/actions/maintenance.yml` to `.github/workflows/maintenance.yml` in the consumer repository. The example follows `@v1-prerelease` and ORM selects its compatible immutable image automatically. Use an exact release tag or reviewed 40-character workflow commit for reproducible workflow selection; that commit must have a published runtime image unless you supply an explicit digest override.
2. Copy `examples/actions/orm.yml` to `.github/orm.yml` on the consumer's default branch. The example reads the proxy URL from the `PROXY_URL` secret and models/efforts from `CODING_MODEL`, `CODING_MODEL_EFFORT`, `REVIEW_MODEL`, and `REVIEW_MODEL_EFFORT` Actions variables. Create those variables with the model IDs and efforts you intend the selected SDK and proxy to use. Plain committed values and custom source names are also supported. Keep credential values out of this file.
3. Add the repository Actions secrets below. The caller example forwards only the selected secrets through the JSON-valued `ORM_CONFIGURATION_SECRETS` secret input, using `toJSON(secrets.NAME)` to preserve quotes and newlines. It also forwards `toJSON(vars)` through `ORM_CONFIGURATION_VARIABLES` as a masked transport, so the runner does not print the variable map in step metadata; those entries remain variable sources. Its map keys match the names selected by `from_secret`; custom names are allowed. Generate the session key once, for example with `openssl rand -base64 32`, and preserve it across runs and upgrades.
4. Use `ubuntu-24.04`, `ubuntu-24.04-arm`, or a compatible Linux Docker runner label through the `runner` input. The runner needs Docker and registry/proxy connectivity; automatic image selection also needs Docker Buildx and GNU `timeout`. Private proxies must be reachable from the temporary container; use a certificate-valid HTTPS endpoint when crossing hosts. Dedicated self-hosted runners must provide the same disposable job/container boundary.

| Secret             | Purpose and permission                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ORM_GITHUB_TOKEN` | Fine-grained PAT restricted to this repository: Metadata, Checks, Commit statuses, and Actions read; Issues, Contents, and Pull requests read/write. GitHub requirement discovery additionally needs the applicable branch-protection/ruleset read permission, including Administration read for legacy protection. Workflow write, workflow approval, and merge authority are unused. |
| `PROXY_URL`        | Reachable compatible model-proxy endpoint, selected by the example configuration.                                                                                                                                                                                                                                                                                                      |
| `ORM_PROXY_KEY`    | Authentication for the configured compatible model proxy.                                                                                                                                                                                                                                                                                                                              |
| `ORM_SESSION_KEY`  | Canonical base64 encoding of 32 random bytes, used for task-state authentication and separately derived artifact encryption. Losing or changing it blocks existing task recovery.                                                                                                                                                                                                      |

The controller uses the job's read-only GitHub token to resolve a default-branch commit and read `.github/orm.yml` by Git object identity. It resolves source references, validates the complete configuration and secret-only credential bindings, then uses the configured PAT for issue and publication operations. Prompt and skill overrides under `.github/orm/prompts/` and `.github/orm/skills/` come from that same pinned commit. It creates root-only runtime configuration and removes the bootstrap token and source maps before starting the runtime child. Defaults are packaged from `examples/workflow` in the pinned image. Overrides replace matching default files and may add regular files; phase references remain explicit in the configuration. Existing symlink, traversal, per-file, aggregate-size, and known-secret checks still apply. The workflow never checks out or executes PR-controlled workflow/setup code with these credentials. Workers receive neither the PAT, proxy key, session key, bootstrap token, source maps, nor artifact credentials.

Newly opened issues start automatically. Edits, reopening, and closure only resume enrolled tasks. Existing backlog requires a maintainer's **Run workflow** selection, using the default branch and `issue-number`. Created issue/PR comments and owned-PR head/closure events are wakeups: authenticated task ownership and current GitHub state decide the work. Recorded automation comments are excluded by identity and receipt; genuine human comments from the PAT account remain eligible input. Reporter/maintainer answer permissions and the frozen bug objective remain enforced by the runtime.

The schedule runs at minutes `7,22,37,52`. It paginates enrolled tasks, including closed issues, to recover replies, review/check changes, or interrupted execution without discovering unenrolled backlog. Up to 256 sorted issues are routed per invocation; larger sets rotate by the 15-minute UTC slot, so their nominal full reconciliation cadence is `15 × ceil(enrolled tasks / 256)` minutes, subject to GitHub scheduling delays. There is no global spending cap. Existing per-task budgets remain authoritative.

Every route resolves the root issue before joining `orm-<repository-id>-issue-<issue-number>` with `cancel-in-progress: false`. A newer pending signal can replace an older pending signal. The surviving invocation reads all unconsumed authoritative input after acquiring the group; event payloads do not represent a work queue. Waiting for replies or CI exits normally and retains no runner. Hard cancellation can recover only the last acknowledged checkpoint and may conservatively consume the saved active reservation. Final cleanup stops and removes only the run-labeled temporary container.

Keep artifacts for the requested 14 days and preserve managed comments, the `orm:managed` label, keys, PRs, and branches. After artifact expiry the existing fresh-audit recovery rules apply. Fix the reported configuration/access/state blocker before resuming through a new event, scheduled reconciliation, or authorized manual selection; never reset budgets or recreate owned work to bypass recovery. To roll back, disable consumer dispatch and return to a compatible pinned workflow/image. Secret installation, consumer repository settings, release publication, and deployment are separate operator actions.

## Run one bounded maintenance task

The default Actions entrypoint processes one explicitly selected issue inside the production container. It reuses investigation, audited bootstrap, implementation, independent audit, real checks, guarded publication, and PR monitoring. It exits when it needs information or remote checks, reaches a future retry deadline, completes, or blocks. It opens no service HTTP endpoint and starts no backlog scan or recurring coordinators; the internal loopback model relay remains.

The pinned reusable workflow prepares root-only runtime configuration at /config/actions.yml from the credential-free [repository configuration](examples/actions/orm.yml) and Actions secrets. Direct controller integrations must supply github.repository/token and proxy.url/key alongside profiles, roles, PR policy, and limits. The strict schema rejects retired webhook, notification, external MCP, and reconciliation settings.

Provide `ORM_SESSION_KEY` through the container environment. Generate it once as 32 random bytes encoded in canonical base64, and preserve the same key for every invocation of these tasks. It authenticates task state; losing or changing it blocks recovery. Keep it with the PAT and proxy credentials, outside worker environments.

Bounded execution requires a verified GitHub Actions run. The trusted caller supplies `GITHUB_ACTIONS=true`, `GITHUB_REPOSITORY`, `GITHUB_REPOSITORY_ID`, `GITHUB_RUN_ID`, `GITHUB_RUN_ATTEMPT`, `GITHUB_SHA`, `ACTIONS_RUNTIME_TOKEN`, and `ACTIONS_RESULTS_URL` to the root supervisor, alongside `ORM_SESSION_KEY`. The repository and run/attempt are checked against GitHub before work starts. The results endpoint must be HTTPS on an Actions results host. Runtime credentials are consumed into protected memory and never passed to coding, audit, or output-review workers. Missing or incompatible context fails before charged work; a standalone Docker invocation is no longer a supported fallback for this entrypoint.

The caller passes one issue number to the default image entrypoint: /usr/bin/tini -- /opt/orm-runtime/bin/node /opt/orm/app/dist/actions/main.js <issue-number>. Use a dedicated container PID namespace on a native Linux AMD64/ARM64 Docker runner. The image has no exposed port or healthcheck. It requires verified Actions context; standalone host execution is unsupported.

Stdout contains one JSON result; diagnostics go to stderr. Results include `version`, `outcome`, a fixed `reason`, verified task identifiers when available, and applicable PR/head or retry identifiers. `waiting` distinguishes `needs_information`, `remote_checks`, `monitor_disabled`, and `retry_scheduled`; `ready` means the existing monitor verified readiness for human review. `out_of_scope`, `no_fix`, and `closed` are separate terminal outcomes. These normal outcomes exit zero, including waiting. `blocked` and `failed` exit nonzero. Exit zero alone is not proof of a completed fix, and human review and merge remain required.

Controller configuration events preserve public repository/run/attempt/issue identifiers, the pinned configuration commit, schema/source metadata, fixed causes and timings even when a configuration secret coincides with a public value such as `0` or `1`. Resolved private settings, configuration contents and source maps are excluded. Records stay within the existing log bound as valid JSON; `omitted_fields` identifies metadata omitted to fit that bound. Missing `.github/orm.yml` reports `config_unreadable` with the checked commit, before task effects.

Collect normal-level diagnostics without attaching to a process or querying task storage:

```sh
gh run view RUN_ID --repo OWNER/REPO --log \
  | rg 'configuration_|model\.request\.|ai\.test\.'
```

Use the run/issue/source fields for configuration events and the shared request/run/job/revision/role fields for relay requests. A relay `deadline_exceeded` cause identifies expiry of its effective request deadline independently of caller cancellation; explicit runtime error codes and `request_cancelled` retain their meanings. `upstream_transport_failed` identifies a connection or transport failure. The cause and recovery text identify whether to correct the trusted configuration, investigate the deadline, or restore provider connectivity before retrying.

Actions task authority lives in one authenticated issue comment, combining reviewed status text and signed controller metadata. The `orm:managed` label is an enrollment sentinel: do not delete it or edit/delete the managed comment. Missing, changed, conflicting, oversized, or incompatible state blocks execution without resetting budgets. The metadata is public, authenticated rather than encrypted, and excludes credentials, raw transcripts, operator configuration, and raw verification logs. State is limited to 32 KiB and the full comment to 60 KiB; exceeding either limit blocks the dependent effect instead of truncating state. The PAT needs issue read/write permission for comments and enrollment labels, in addition to the existing publication permissions.

SQLite at `/data/actions/<issue-number>/state/manager.sqlite` and its sibling runtime directory remain local working storage. At a coherent, idle checkpoint the supervisor exports a consistent SQLite backup, required native session/manifests, and changed workspace contents relative to verified Git source. Original source is fetched and verified again during restoration. Credentials, SDK authentication files, dependency caches, worker homes, Git configuration, and installed toolchains are excluded. Tool environments are rebuilt from the retained audited plans and checked against their recorded identities.

Bundles are compressed before AES-256-GCM encryption. The encryption key and comment-authentication key use separate HKDF purposes derived from `ORM_SESSION_KEY`. Only ciphertext is uploaded with pinned `@actions/artifact` 6.3.1, requesting 14-day retention; the verified effective expiry is recorded. A bounded root-only helper keeps artifact SDK credentials and logs outside worker environments and the JSON result. The PAT additionally needs Actions read permission for previous-run artifacts. The comment references the exact repository/task/checkpoint, originating run and attempt, artifact ID, ciphertext digest/size, and expiry. It is updated only after upload verification and acknowledged readback. Graceful shutdown attempts a final idle checkpoint after worker cleanup, within the existing shutdown deadline. Failure is reported with `checkpoint_failed: true` and retains the previous artifact reference. Hard termination preserves only the last acknowledged checkpoint.

A fresh container verifies provenance, encryption, supported schema/runtime, source and snapshot compatibility, sizes, paths, and content digests before importing working state. The existing worker storage limit also bounds bundle size and expansion; manifest limits remain 16 MiB and 100,000 entries. Restored budgets cannot replace newer durable counters. Pending publication is reconciled before new effects; missing required evidence blocks further execution rather than creating another PR. Confirmed artifact expiry or deletion produces a visible managed-comment notice and `session_recovery: expired_or_deleted` in the result. Eligible unpublished work can start a fresh conversation from durable findings after compatibility checks; task identity, budgets, frozen scope, and published ownership survive. Corruption, missing credentials, unknown schemas, incompatible state, and inaccessible artifact metadata block execution. Owned PRs can recover after artifact loss from authenticated continuation state: the controller fetches the exact recorded head, obtains a fresh independent audit and runs real checks within the remaining task budgets before monitoring or repair. Recovery never invents prior execution receipts or creates a replacement PR. Missing frozen scope or publication provenance, incompatible state, and ambiguous writes remain blocking. Existing authenticated comments with a null artifact reference remain readable.

The controller continuation interface separates immutable task input from `conversation: { version: 1, id, messages }`. Admitted messages carry a stable ID, content, and the digest produced by the shared `digest(content)` helper. Only unacknowledged messages are appended to native history. Repeated acknowledged messages return the saved result without starting another worker; reusing an ID for different content fails. Actions admits new issue comments only for an outstanding reviewed question. The reporter may supply facts; users whose current repository permission is write, maintain, or admin may supply facts or clarify intended existing behavior. Recorded automation output and bot replies are excluded without excluding human comments from the PAT owner. Admitted comment IDs and content digests remain fixed; changed or missing admitted replies block continuation. Replies never grant authority to expand the frozen bug objective. Audit and output-review sessions always start fresh. Unknown legacy local-only databases remain blocked for operator inspection.

Actions can ask for clarification during investigation, implementation planning/coding, and repair. It prepares and reviews a separate question comment, saves an idle encrypted checkpoint and publication intent, posts the question, verifies readback, and exits with `waiting/needs_information`. The authenticated status comment remains the task authority. A reply posted before question readback is still discoverable. Duplicate invocations with no new admitted answer start no worker; insufficient answers can produce another reviewed question. Human waiting has no task-expiry deadline and consumes neither active-work nor CI-wait allowance. After native artifacts expire, unpublished work starts a fresh conversation from durable findings and any frozen scope, preserving identity and budgets. An existing owned PR follows the same fresh-conversation policy after its recorded head passes fresh independent audit and real checks. Human head changes block recovery. Existing legacy questions are reissued for maintainer-only answers when no compatible continuation exists. The reusable workflow invokes the entrypoint for new activity and scheduled reconciliation.

The shared eligibility gate classifies requests before dependency bootstrap. Only an evidenced violation of existing supported behavior may enter implementation, supported by controller-recorded reproduction or independently reviewed source analysis. Labels and maintainer preference do not establish a bug. Feature and architectural requests receive an explanation and remain open. Historical generic maintenance candidates without the new bug-evidence contract cannot proceed to coding.

When the current head passes configured automation, Actions updates the managed status and publishes one deduplicated readiness comment. Authenticated intent and authored-comment readback reconcile response loss; repeated invocations do not create duplicate notices. Every readiness publication rechecks current head, checks, reviews, and policy.

Serialize **all** invocations for the same repository and issue through one caller. The runtime serializes its comment writes and checks generations/readback, but GitHub comments do not provide a transactional distributed lock. Different issues may run independently. A publication response loss must be reconciled against the recorded branch/PR and intent; it never permits a second PR. Preserve comments, labels, keys, and published work on rollback, and disable dispatch rather than treating existing tasks as new.

SIGINT/SIGTERM abort active work and initiate verified worker cleanup, relay shutdown, checkpointing, and database closure. Cancellation exits nonzero; cleanup or checkpoint failure cannot produce success. Shutdown retains a ten-second deadline. Hard termination promises only the last acknowledged remote checkpoint. Recovery charges elapsed active time since that checkpoint through its original deadline, so a long outage can exhaust the remaining active allowance. Future retry deadlines are returned without keeping the container alive. State failures have fixed `state_*` reasons; `recovery_evidence_missing` identifies an owned publication whose local continuation evidence is unavailable. Verified results also identify the task UUID, canonical comment ID, and acknowledged generation.

## Protected configuration and workflow bundles

[examples/actions/orm.yml](examples/actions/orm.yml) defines repository configuration containing source names rather than credential values. The controller binds the repository identity to the trusted Actions context and resolves values before producing /config/actions.yml. Direct runtime integrations supply fully resolved values in that protected file; references are a repository-configuration feature. Unknown fields and unsupported versions fail. There is no environment interpolation, source fallback, include processing, or storage migration.

Configuration values use one of these forms:

```yaml
proxy:
  url: https://proxy.example.com/v1
# Alternatively, replace that URL value with either:
# { from_variable: PROXY_URL }
# { from_secret: PROXY_URL }
```

A reference reads exactly one named source. `from_variable` uses the caller's Actions `vars` context forwarded through the masked `ORM_CONFIGURATION_VARIABLES` transport; `from_secret` uses the explicit `ORM_CONFIGURATION_SECRETS` map. Names are case-insensitive. Missing sources fail rather than selecting a value from another store. Literal values never consult either store. Each reference accepts only its selector and optional `format: json`; mixed selectors and unknown reference options fail.

```yaml
limits:
  repair_cycles: { from_variable: REPAIR_CYCLES, format: json }
pr_monitor:
  enabled: { from_variable: MONITOR_ENABLED, format: json }
```

Store `0` and `false`, respectively, for those JSON examples. References default to unchanged text; JSON decoding is opt-in for numbers, booleans, arrays, or objects. Decoded JSON is data: nested lookalike references are not evaluated. The resolved configuration must still satisfy every schema, role-reference, model/effort, path, and budget constraint. Shared references are allowed, including the same effort variable for several profiles. Source maps are limited to 64 KiB each; YAML and resolved configuration are limited to 1 MiB. Recursive aliases and excessive nesting are rejected.

`github.token`, `proxy.key`, and `session_key` must originate from `from_secret`, including when their containing object is supplied as secret JSON. Committed or variable-sourced credentials are rejected. The repository identity remains trusted Actions context and cannot be selected through configuration. Only selected secret values are retained as root-only redaction metadata; unreferenced source maps are not passed to the runtime. Redaction metadata is excluded from snapshots. A secret-sourced ordinary setting still follows its normal projection: models and efforts reach their SDK, while authentication credentials remain outside workers and snapshots.

Configuration events use the existing unfiltered INFO/ERROR logger methods on stderr. `configuration_source_resolved` records the selected store/name, safe line/column, pinned commit, schema version and run/issue correlation; `configuration_load_failed` records a fixed cause and expected/observed type. Values and source payloads are omitted, and referenced secret values are redacted independently of credential scanning. Collect the run with `gh run view RUN_ID --log` and filter for `configuration_source_resolved`, `configuration_resolved`, or `configuration_load_failed` and the issue/run IDs. For `source_missing`, supply the named variable or forwarded secret; for invalid JSON or schema types, correct that source value or its `format`; for `github_access_denied` during configuration loading, restore the job token's Contents read access. Workflow logs retain the existing GitHub Actions retention policy; logger messages retain the 2 KiB per-message cap.

The runtime configuration must be a root-owned regular file with owner-read permission and no group/other permissions, in a root-owned directory without group/other write access. Symlinks, including parent components, are rejected. Mount configuration, /prompts and /skills read-only. Startup validates the configuration and all selected bundles before task execution. Diagnostics use fixed codes and safe locations, excluding credentials and source contents.

Each named profile requires `sdk`, `model`, and `effort`. Every phase selects a profile independently: `bootstrap`, `investigation`, `implementation`, `audit`, and `output_review`. Claude accepts `low`, `medium`, `high`, `xhigh`, and `max`; Codex accepts `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, `ultra`, and `persistent`. These are SDK-level values; a model may support a subset. Model IDs, including proxy aliases such as `auto`, are passed directly to the selected SDK without a runtime model catalogue or `behaves_as` mapping. The configured effort is passed to the SDK unchanged. The relay supplies it when omitted and rejects a different wire value. SDK/provider compatibility is the operator's responsibility; errors fail without fallback. Remove retired `behaves_as` fields from existing configurations. The Codex adapter forwards `minimal`, `low`, `medium`, `high`, `xhigh`, and `max` exactly. It rejects `ultra` and `persistent` before inference because the pinned CLI rewrites those aliases; provider/model errors fail without changing model or effort. See the [Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) and [Claude effort documentation](https://platform.claude.com/docs/en/build-with-claude/effort).

`roles.<role>.prompts.system` and `.user` name UTF-8 files relative to `/prompts`. `roles.<role>.skills` lists directories relative to `/skills`, each with a `SKILL.md`. The loader copies all regular files below each selected skill directory, including contained reference files and binary assets. It never follows Markdown links or executes a bundle file while loading. Absolute paths, `..`, symlinks, missing files, writable-by-group/other bundle content, and known credentials in content or metadata are rejected. Files are limited to 1 MiB each, with a 16 MiB aggregate loading limit across roles; configuration YAML is limited to 1 MiB and bounded alias expansion.

The loader exposes a deeply frozen, JSON-safe `RunSnapshot` with a digest, role profiles, prompt text, and skill bytes encoded as base64 with per-file digests. `snapshot.settings` is supervisor metadata and includes non-secret upstream configuration; pass only `snapshot.roles[role]` to a future worker. Role projections exclude upstream endpoints, credentials, and authentication headers. The separate root-only `SecretAccessor` supplies credentials and known-secret checks; it is not part of the snapshot. Known-secret checks detect configured values, not arbitrary unknown secrets.

Configuration and bundle content load once at startup. Restart to load edits; previously captured snapshots remain self-contained and unchanged. Each issue workflow keeps its original persisted snapshot even after restart or later activity; newly enrolled workflows capture the current snapshot. The mounted investigation, implementation, audit, review-feedback and output-review examples support the complete workflow. Readiness policy is supervisor configuration: after restart, edits apply to existing PR monitors and invalidate their prior readiness evidence without changing coding snapshots, model profiles.

The runtime has one active slot per invocation. Defaults are 60 active minutes, 200 model requests, three repairs, two infrastructure retries, and 24 hours of CI/review waiting per task. Worker defaults are 128 processes, 16 MiB aggregate output, and 4 GiB monitored storage. Budgets survive issue activity and restarts. Waiting for a human reply consumes neither active-work nor CI-wait budgets.

Structured SDK output is validated locally with AJV and RE2. JSON Schema 2020-12 and draft-07 are supported; unsupported patterns and external schema references fail without fetching remote resources.

## Selected issue intake and storage

Enrollment verifies the configured GitHub repository and reads only the selected issue. Monotonic per-issue refresh generations prevent overlapping reads from applying stale state. Owned comment IDs exclude automation output while preserving genuine human replies from the same PAT account. Closure, reopening, scope changes, publication ownership and revision fencing remain authoritative.

Local SQLite uses WAL, full synchronous commits, prepared statements and transactions under a supervisor-owned 0700 directory with 0600 files. Schema version 12 is initialized only for a fresh database; version 12 can reopen. All earlier and unknown versions are rejected without migration or reset. Workers cannot access it. Authenticated task comments remain authoritative over restored local budgets and publication state. Preserve committed WAL state when taking a backup.

## Automatic issue investigation

Each bounded invocation advances its selected issue through one execution slot. Each investigation reads pinned source, proposes citations and optional reproduction commands, obtains audited setup when needed, and executes reproduction under the coding UID in a fresh source workspace. Nonzero reproduction exits are recorded with command, environment, source, revision, and bounded output; they are not confused with setup success. Source citations are resolved from supervisor-controlled Git objects. Model claims and SDK transcripts alone are not evidence.

Structured outcomes are `maintenance_candidate`, `needs_information`, `no_fix`, `manual_feature`, and `blocked`. Maintenance requires a concrete objective and supervisor-recorded reproduction or independently reviewed source proof. Source-only findings say **not reproduced**. The exact findings and evidence pass the existing scanner and independent output review before publication. A confirmed publication queues maintenance with `phase: implementation`; the same serialized coordinator automatically consumes that handoff. Features remain manual even when a maintainer accepts the idea. Information requests use reviewed question comments; handoffs and blockers remain visible in the managed status.

The publisher updates one durable instance-owned comment. Fixed stage templates retain the exact previously reviewed summary, its original inspected SHA, and an owned PR reference when available. Changed narrative requires new review. Pending comment writes are reconciled before applying issue activity, so a lost publication response cannot become fresh human input. A genuine comment by the PAT owner is still input. Closed issues cancel work and retain their last comment. Human edits or deletion of the owned comment block publication instead of being overwritten or replaced.

Completed information/no-fix/feature investigations rerun only after issue edits, human comments, or reopening. A default-branch change invalidates active investigations and queued maintenance handoffs. Snapshots and lifetime budgets survive all revisions and restarts. Model/review/evidence failures stay blocked; only classified transient failures receive bounded infrastructure retries. Cancelling an invocation cancels active work while retaining checkpoints. Only guarded supervisor publication can mutate GitHub.

## Automatic maintenance implementation

Confirmed reproduced and reviewed source-only maintenance candidates enter a durable implementation pipeline. The coordinator freezes the original objective, acceptance criteria, edit paths and discovered local checks before coding. A job-owned branch starts from the recorded default-branch SHA in a credential-free workspace. The implementation role adds a real regression; a fresh independent audit inspects the entire immutable candidate. Features, unrelated/protected edits, weakened checks and mismatched receipts cannot advance.

After a matching audit, the supervisor restores that candidate and executes Linux-local repository checks under the audit verification UID (10002), separately from coding workers. Receipts identify commands, working directories, environment identity, source/artifact/scope digests, actual exits and bounded output digests. Source integrity is checked around setup and every command. Failed tests or audit findings can return to implementation within the lifetime repair budget (three by default); changed candidates require fresh audit and test evidence. Missing local infrastructure blocks the job. Discovered remote-only checks remain explicitly pending.

The existing scanner and output review gate the exact candidate before normal publication to the recorded instance-owned branch and one non-draft PR. The PR includes the issue-closing reference and audit/test summary. One owned issue comment reports the actual stage and retained investigation evidence. Successful publication enters `remote_review`, releases the execution slot and hands the PR to durable CI/review monitoring. Readiness comments require current-head evidence. No automatic merge occurs.

Checkpoints retain completed audits, tests and publication operation IDs across retries and shutdown. Publication response loss is reconciled before more mutation; unexpected human branch changes and default-branch drift block publication. Closed or revised issues cancel the old candidate. Once an owned PR exists, subsequent issue/PR activity stays in remote waiting rather than creating another first-publication pipeline. Operator-mounted implement and audit skills guide model behavior; repository text cannot expand the frozen scope.

## PR feedback and current-head readiness

After first publication, the supervisor monitors only PRs recorded as owned by this instance. The reusable workflow routes owned-PR activity and scheduled reconciliation to the selected issue; the runtime reads current state. Full REST/GraphQL pagination includes conversation comments, reviews, review threads, every nested reply, reactions, check attempts and statuses. Waiting releases the coding slot. A separate lifetime 24-hour wait budget includes downtime; restarts, new commits and policy edits do not reset it. Active/model limits, the three-repair ceiling and two infrastructure retries remain shared with the original job.

`pr_monitor` defaults to `enabled: true`, `requirements_source: github`, empty `required_checks` and `automated_reviewers`, and `local_checks_only: false`. The monitor reads legacy branch protection and applicable rulesets and combines discovered required checks with operator additions. Required source/integration identities are retained. Unknown/inaccessible requirements block readiness. To attest a complete checklist when discovery is unavailable or includes an unsupported automation rule, explicitly select `requirements_source: operator` and supply `required_checks`. Known discovered checks remain mandatory. An empty result set is never success; explicit local-checks-only policy is accepted only when no GitHub CI requirement or unknown requirement exists. The example lists this repository's additional CI/security/review gates. `{pr}` in a configured name expands to the owned PR number.

`automated_reviewers` entries contain `login` and `signal: github_review|codex|coderabbit`. Generic reviews must name the current SHA. Codex and CodeRabbit support their bounded no-findings signals only from the verified bot identities during the current head's review cycle. A newer in-progress indicator, absent completion, unavailable reviewer, quota/rate limit, failed, cancelled, neutral, skipped or pending required check blocks readiness. A CodeRabbit rate-limit notice is not a completed review in this runtime. Human approval remains a separate merge gate and is never granted by the monitor. The runtime does not trigger/retry remote workflows or update the base branch automatically.

The implementation role assesses each actionable surface against the frozen scope and actual candidate. Candidate-file citations and controller audit/test receipts support dispositions; thread resolution and outdated anchors alone establish no fix. Assessment cannot change source. Valid corrections return to the existing implementation/audit/unprivileged-test/scanner/output-review pipeline, then advance the owned branch normally. Feedback replies and supported resolutions use the durable publication journal. Interrupted effects are observed by exact IDs/markers before any further mutation. Unknown scope, human branch changes, insufficient CI evidence, exhausted budgets and timeouts remain visible operator handoffs.

When every current-head gate and finding disposition is complete, the existing owned issue comment says **Automation clean; awaiting human review**. A deduplicated readiness comment identifies the head. Check/review activity or changed policy invalidates the evidence; each publication revalidates GitHub. A readiness comment is not permission to merge and does not prove the branch is current with then-current main; the maintainer must validate the merge candidate and required human review.

## Supervised worker runtime

The runtime supports the dedicated Linux container with exclusive `coding` (10001), `audit` (10002), and `output-review` (10003) identities. Do not share its PID namespace with host processes or unrelated services. `AgentRunner.run(request, AbortSignal)` streams validated progress, usage, artifact, session and terminal events. SDK modules are registered by supervisor composition and load only inside the unprivileged worker. Production registers Claude Agent SDK 0.3.296 and Codex SDK/CLI 0.162.1. The root process registers their module paths and imports no vendor SDK. The investigation coordinator dispatches enrolled issues through this runtime.

Each run receives a fresh disk-backed home, workspace and temporary folder under `/data/actions/<issue-number>/runtime/runs`, with read-only materialized operator bundles. Supervisor-authenticated Git fetches retain the pinned commit and all reachable ancestors in protected staging. Worker checkouts receive fresh Git configuration and independent objects, with no PAT, upstream key or retained credential helper. Submodules and LFS downloads are not automatic. Repository setup uses the callable audited bootstrap stage described below; the investigation coordinator requests setup when reproduction needs a project environment. Workers launch with explicit UID/GID drops, cleared groups/capabilities, no-new-privileges, clean environments and process limits. Parent and detached descendants are terminated before an account is reused.

The model relay listens only on loopback. Short-lived run authorization grants the configured profile's Messages/token-counting or Responses/compaction HTTP routes. The supervisor supplies upstream authentication, rejects redirects and WebSockets, persists a shared request reservation before forwarding, and aborts cancelled, expired or stale work. Failed requests still consume reservations. Worker output is untrusted; a clean exit and terminal event alone do not approve publication.

After process cleanup, candidate files are copied into supervisor-owned digest-addressed blobs and manifests. Root never reads worker Git configuration. Escaping symlinks, hardlinks and special files are rejected; safe relative symlinks are preserved without following them. Accepted receipts bind the artifact to its job/revision and source commit. Session identities are fenced by source, role, profile, prompt snapshot and immutable input identities. Claude exports only native transcripts and contained sidecars into a run-private session folder; Codex exports the matching native JSONL transcript and version/binding/usage metadata. After UID-wide process cleanup, root seals conversation and workspace manifests under protected `private/sessions` storage. Completed coding runs and clean Claude SDK-limited runs may resume with matching immutable input and optional `output_schema`; the explicit controller conversation interface appends newly admitted messages separately; consumed request/time budgets remain charged. Codex failed or supervisor-limited runs create no new checkpoint. A limited checkpoint is never a publishable artifact. Failed, cancelled, stale, crashed, or cleanup-failed runs cannot supply a new checkpoint. Missing/corrupt checkpoints, SDK-version changes, or binding changes fail explicitly; older session-ID-only receipts are not resumable. Independent reviews always start fresh.

Claude loads the selected immutable system/user prompts and phase skill files explicitly. Repository/user settings, hooks, plugins, automatic skills/memory, SDK delegation, and interactive permission escalation are disabled. Coding roles receive Bash, Read, Glob, Grep, Edit, and Write; audit receives Bash and the reading tools; output review receives only Read, Glob, and Grep. The SDK receives empty MCP configuration in strict mode and rejects any active external server. These controls complement the supervisor boundary. Optional caller-owned JSON output schemas are validated locally; SDK errors, missing/invalid output, cancellation, and limits cannot become successful terminal results. Usage includes cached input tokens and subtracts known prior-session totals rather than counting resumed history again.

Codex uses a custom Responses provider over HTTP/SSE with WebSockets and transport retries disabled. A fresh Codex home and explicit untrusted-project settings prevent repository configuration from adding providers, hooks, MCP servers, skills or plugins. It loads the operator prompts and selected skills explicitly. Shell commands receive a separate clean environment without relay authorization or login-shell inheritance. Coding and audit execute within the existing container UID/workspace boundary; Codex's additional shell sandbox is disabled for these roles. Output review consumes the supplied payload and supporting evidence, with shell and external MCP access disabled and native file writes denied by a read-only policy. Codex drains the event stream through successful process exit and validates structured output locally before completing. Native usage is cumulative: cached input and reasoning output are already included in totals, known prior totals are subtracted on resume, and unknown usage is omitted.

An independent audit/output reviewer can run in the parent's existing lease while the requesting coding or audit process tree is suspended. The reviewer uses fresh workspace/context and immutable input, with the parent budget still enforced.

Disk usage is checked every second, including source staging, workspace/home/temp folders, role-owned shared temporary files and open deleted files. Verified Git objects move into the fresh checkout without duplication. A credential-free trusted probe uses the worker's effective identity to inspect deleted files while retaining protected root real/saved identities; workers cannot signal or inspect the probe. Deleted mappings without a measurable descriptor and other monitoring errors cancel the run. Exceeding a configured threshold also cancels the run. These are soft limits on ordinary disk storage, with no tmpfs requirement or hard filesystem quota. A rapid writer can exceed a threshold before detection and fill shared storage. Installer storage accounting bounds growth during each operation; operators size retained toolchain and download storage separately. Preserve space for state and artifacts when sizing the data volume. Cancel work and verify cleanup before replacing a running container; preserve authenticated task state and publication receipts.

## Audited repository bootstrap

`Supervisor.bootstrap.prepare(request, signal)` prepares the pinned source and returns a durable setup receipt. Internal callers attach its ID as `bootstrap_receipt` to later agent requests. Investigation and maintenance call this capability when their commands require project tools. A setup failure blocks the selected task and is reported in its bounded result.

The configured bootstrap SDK inspects source and proposes a strict structured plan. A fresh audit worker independently approves the exact source and plan digests before installation. Plans contain exact Go/Node/Python versions, signed distro package names, exact package-manager versions, unprivileged setup commands, and proposed local/remote test commands. Bootstrap verifies tools and setup; investigation owns project test execution. Windows requirements remain recorded remote checks.

Mise v2026.10.9 is pinned by architecture-specific checksums. Its built-in installers run in private supervisor configuration with safe mode, hooks/plugins/default packages disabled, and download verification enabled. Node signature/checksum checks and Python artifact attestations are required; unsupported precompiled versions fail without source-build fallback. APT accepts package names through fixed commands, trusted image sources, and no-removal policy. Distro and toolchain vendors remain trusted privileged-code suppliers.

Public Go modules, npm, pnpm, Yarn Classic/current Yarn, pip/venv, Poetry, and uv are supported. Package managers install as workers in private run directories. Standard sources are the public Go proxy/checksum service, npm/Yarn registries, and PyPI. Existing usable locks or complete pinned requirements are required when dependencies are needed; missing/stale locks, credentials, custom registries, unavailable versions, and failed setup block explicitly. npm's `private: true` publishing flag does not by itself indicate private dependencies.

Shared toolchains are supervisor-owned and read-only. Each coding/audit run receives independent writable dependency environments and caches. Setup cannot change manifest or lockfile fingerprints. Generated dependency state is excluded from artifacts and rebuilt on fresh/resumed runs; existing source is preserved. Supervisor and SDK launchers retain the fixed runtime while project commands use verified tool paths.

Receipts bind job/revision, pinned source/artifact, prompt snapshot, plan/audit, manifest/lock fingerprints, platform, package inventory, installer/tool integrity, exact versions, and actual command results. Changed identities invalidate reuse and resume. Installation intent precedes mutation; interruptions remain recorded and partial/unverified installations block reuse. Inspect damaged package or tool state before retrying; do not remove shared packages or caches automatically. Disable consumer dispatch and cancel any active invocation before operator recovery; verify worker cleanup and preserve the last acknowledged checkpoint.

## Reviewed GitHub publication

`Supervisor.publication.publish(proposal, signal)` is a callable supervisor capability. It accepts status text, structured investigation findings, fixed investigation/PR-stage updates, reviewed feedback replies and resolutions, a fixed operational-notice reason, or a change proposal with a frozen artifact, expected bot head, and supervisor-recorded audit/test evidence IDs. `recordEvidence(evidence, signal)` scans and stores immutable evidence bound to the job/revision, source and artifact. The maintenance pipeline supplies independent audit and actual supervisor-executed test evidence; worker claims alone are not receipts. Investigation, implementation and PR monitoring invoke this publication gate; there is no HTTP mutation endpoint.

`publication.outputReview.review(request, signal)` and `verify(receiptId, request)` provide the reusable external-output gate. The request binds destination identity, exact payload, evidence, artifact, policy and job snapshot. Structured strings and keys receive known-secret and pinned Gitleaks 8.30.1 checks. Scanner rules and ignores come from isolated supervisor storage; repository suppressions and inline allow comments have no authority. Scan/review errors block publication with safe codes. Unknown secrets can still evade heuristic detection.

Decoded YAML scalar scanning includes duplicate keys, plain and quoted folding, and block scalars. YAML artifacts must parse completely. Scanner inputs are limited to 1 MiB per text field and 32 MiB in aggregate, with bounded document depth and node counts; incomplete coverage blocks publication.

Every generated payload uses a fresh `output_review` context without write credentials or MCP access. Nested review suspends the requesting coding or audit process and shares its existing lease and time/model budgets. Changed payloads or destinations invalidate approval. Fixed notices for model unavailability, budget exhaustion and publication blockage use checked templates without a model request. Select the sample `output-review` skill in the operator bundle; existing snapshots retain their original bundles.

The publisher preserves one owned status comment and one owned open PR per issue. Its branch namespace derives from the persisted instance ID and issue number. It rejects default/protected branches, branch rules, workflow/action definitions, CODEOWNERS, Dependabot configuration and submodule changes. Ordinary GitHub documentation and templates remain eligible. New/changed files must be UTF-8 text or contained symlinks; changed binaries and archives block explicitly. Unchanged binary blobs already on the remote remain intact.

After digest and link validation, a clean supervisor-owned Git repository constructs one commit from final blobs with filters and hooks excluded. Worker history is never imported. Commit attribution uses the authenticated PAT account and its GitHub noreply address; timestamp and metadata are frozen before transmission. Only normal branch advances are supported. Source drift, human edits, missing/closed owned objects, and changed heads block further writes.

Publication intent precedes each transmission. Exact markers, IDs, bytes and remote heads reconcile confirmed effects, including after restart or a changed job revision. `publication.reconcile(operationId, signal)` observes an interrupted operation without transmitting another write. An absent object after an ambiguous create remains uncertain; another create is blocked until inspection. Confirmed operation replay returns its stored receipt. Intake-observed heads never replace the last confirmed publisher head.

Publication and reconciliation serialize per issue. Provider backoff persists across restarts, and subsequent safe observation retries consume the job's infrastructure retry budget. Legacy ownership without confirmed target state blocks new objects. Reviewed PR title/body changes may reuse the confirmed branch head without creating a commit.

Preserve authenticated task state, artifacts and publication receipts when changing the pinned runtime. Human review and merge remain required.

## Releases and version references

Successful Repository CI and CodeQL main-push runs automatically start the prerelease workflow. It requires both latest-attempt validations for the exact same source SHA, same-repository provenance, and the current main revision. PR checks, cancelled or failed validation, and superseded sources do not publish candidates. CI keeps its existing cancellation policy; rapid merges can supersede intermediate revisions. The workflow runs its own publication jobs directly, so it does not depend on events generated by `GITHUB_TOKEN`.

The first candidate is `v1.0.0-rc.1`. Further validated revisions increment `rc.N` until stable promotion; after `v1.0.0`, the next candidate becomes `v1.0.1-rc.1`. `package.json` supplies the minimum intended release base. Bump its stable version and the lockfile root version together in a normal PR to start a minor or major line, such as `1.1.0` or `2.0.0`. Ordinary patch progression does not create version-bump commits or require a package edit.

Each candidate reserves only an immutable Git tag before building on native `ubuntu-24.04` and `ubuntu-24.04-arm` runners. Both digest-addressed images must pass bounded default-entrypoint startup, source/platform identity, Node/SQLite execution, and bundled native-tool smoke checks. Only then can it publish and verify the combined image, create a published prerelease (`draft: false`, `prerelease: true`), attach and read back `publication.json`, and update the major prerelease aliases. New candidates never create draft releases. New image proofs bind the source, release version and native digests before a GitHub release ID exists; old proofs and receipts remain supported for verification and stable promotion.

| Channel   | Exact Git tag | Moving Git tag  | GHCR tags                                             |
| --------- | ------------- | --------------- | ----------------------------------------------------- |
| Candidate | `v1.0.0-rc.N` | `v1-prerelease` | `1.0.0-rc.N`, `1-prerelease`, `sha-<full-source-sha>` |
| Stable    | `v1.0.0`      | `v1`            | `1.0.0`, `1`, `latest`                                |

Future majors follow the same pattern: `v2-prerelease` and `v2`, with `2-prerelease` and `2` image tags. Numbered Git and image references cannot be replaced by retries. Moving Git aliases are annotated tags naming their exact release. Stable and prerelease aliases are separate; publishing a candidate never changes stable aliases or `latest`.

To publish stable, dispatch **Promote stable release** from `main` and provide the latest published, verified RC for the active base:

```sh
gh workflow run promote-release.yml --ref main -f source_rc=v1.0.0-rc.3
```

A package-version bump on current `main` starts the intended line immediately, so older RCs cannot be newly promoted while the new line is awaiting validation or building. Retries of an already completed matching stable publication may repair its aliases while it remains the latest stable release for its major; repairing an older major never changes global `latest`.

The workflow derives `v1.0.0`, verifies source ancestry, exact-source main CI, the candidate tag, durable receipt, image digest and both native manifests, and copies that existing multi-architecture index. It does not rebuild. Candidate and stable digests must match exactly; OCI version labels retain the original RC version. The prerelease remains available. A conflicting existing stable tag, source, image or receipt blocks publication.

Consumers can call `markhuangai/opensource-repo-manager/.github/workflows/maintenance.yml@v1` for the latest published stable `1.x.x` release or `@v1-prerelease` for the latest published `1.x.x-rc.n` prerelease; the same references work for `test-ai.yml`. There is no root action. Both reusable workflows accept an optional `runtime-image` override. When omitted or empty, a runtime job inside the called workflow runs once per invocation and selects `ghcr.io/markhuangai/opensource-repo-manager:sha-<workflow-commit>` using GitHub.com's called-job workflow identity, rather than the consumer's commit or a separate moving alias. It verifies the source-bound version-2 publication proof and both smoke-tested native manifests, then passes one immutable `@sha256:` reference to routing and every maintenance job, or to the AI test. The runtime job receives no configuration secrets and needs no additional caller permissions.

Exact release tags and full workflow commit pins use the same source-bound selection. An unreleased commit may have no image; wait for its successful main validation and automatic prerelease, or provide a known-compatible immutable `runtime-image` from a verified release's `publication.json`. Explicit overrides keep the existing digest validation, support other image repositories, and bypass automatic lookup and job-identity requirements. Missing identity, unavailable images, invalid proof, and architecture mismatches fail before configuration secrets reach a runtime container. The resolver never substitutes another release.

Image-selection logs use normal Actions visibility. `runtime.resolved` records the selected digest, source and release version; `runtime.used` connects each consuming job to that digest. `runtime.failed` identifies the stage, expected/observed proof, provider status and error, elapsed time, and recovery action. Registry inspection has a 60-second deadline and no automatic retry. Public manifest captures are limited to 64 KiB and provider-error captures to 16 KiB, with omissions reported explicitly; an oversized manifest fails selection. Configuration and credentials are excluded, and log retention follows the existing Actions policy. Collect one invocation with `gh run view RUN_ID --repo CALLER_REPO --log | rg 'runtime\.|::error::'`. For registry failures, verify GHCR connectivity and publication for the logged workflow commit; for proof failures, inspect the logged public manifest and select or repair the matching workflow/image pair.

Candidate and promotion runs serialize independently. Their reservation/finalization steps share a release-state concurrency lock, so they cannot simultaneously change release authority. Older pending candidate runs may coalesce. The shared lock protects GitHub and registry mutations; main can still advance during a build, in which case publication fails with a superseded-source diagnostic and the new validated main revision supplies the next candidate.

After an interruption, inspect the failed stage before rerunning the same Actions run. Completed candidates can repair their major aliases after main advances; replaying an older RC never replaces a newer candidate within that major. Matching completed versions and durable receipts are reused; an index already published before receipt upload is verified and recovered without replacement. One-day architecture artifacts may expire, so an unfinished build can require rebuilding untagged native digests. Legacy draft and orphaned tag reservations are retained as evidence, and newer sources allocate a later RC. Release creation and receipt upload are separate GitHub operations: an interrupted upload can leave a published prerelease with its verified image digest in the body but no receipt asset yet. Rerunning recovers the same image and release; moving aliases stay unchanged until receipt readback passes. Never delete or move numbered tags to bypass a conflict. Failed native builds can leave untagged digests, as before; release tags are published only after both native smoke tests pass.

Release logs use normal Actions visibility and structured `release.*` events. They include repository, run/attempt, stage, source/version, CI decisions and run URLs, platform/digest evidence, durations, outcomes and causal errors. Collect one operation with:

```sh
gh run view RUN_ID --repo markhuangai/opensource-repo-manager --log | rg 'release\.|::warning::|::error::'
```

The last completed stage and error's recovery field identify whether to wait for current-main validation, repair the native build, correct access/provider failure, or inspect a conflicting tag/receipt. Debug logging is optional; required evidence is emitted without enabling it. Logs use the repository's existing Actions retention. Release assets retain durable publication receipts beyond the one-day architecture artifacts; credentials, environments and authentication headers are excluded.

GHCR package visibility remains an operator setting. Ensure the package is public and verify anonymous pulls for both supported platforms before announcing anonymous availability. This PR delivers automation; it does not dispatch a release, change package settings, deploy consumers, or merge itself. A human merge activates automatic prereleases for subsequent successful main validation, including that merge when eligible.

## AI pull request review

Trusted maintainer PRs start review through `pull_request_target`; other-author and fork PRs use successful PR CodeQL completion. Trigger changes in the trusted review workflow take effect after human merge. A manual dispatch accepts an open PR number. The initial workflow bootstrap had a one-time activation exception; later PRs require their own successful review status. Ordinary CI remains automatic, with no review-first request controller.

The AI reviewer follows `v1-prerelease` and uses Claude, a variable-configurable model defaulting to `auto`, effort `xhigh`, six isolated goals, 200 turns per goal, a 50-minute review limit, and no automatic approval. Its goals cover design, security, reliability, public contracts, scope/operations, and test assurance. It first reinspects claimed fixes, then independently sweeps the full change. It runs separately from builds with a pristine checkout and read-only tools. Per-PR concurrency, duplicate suppression, and exact-head status fencing prevent stale success. ## Security boundaries

Configuration and credentials remain in the root supervisor. Coding, audit, and output review use distinct unprivileged users, fresh environments and credential-free workspaces. The loopback model relay supplies upstream authentication outside SDK processes; only guarded supervisor publication writes to GitHub. External MCP tools and Discord/SMTP/HTTP notification integrations are absent.

Agents retain direct outbound networking and can upload source they can read. Separate users do not prevent container or kernel escapes because Docker shares the host kernel. Use standard Docker without a host socket, privileged mode, host networking or NET_ADMIN. Root toolchain installation trusts the configured distribution, mise and upstream vendors; arbitrary model-generated root commands and repository root hooks remain excluded.

Automatic merging, force pushes, repository-setting changes, private registry credentials and approval of privileged workflows remain outside the runtime's scope.
